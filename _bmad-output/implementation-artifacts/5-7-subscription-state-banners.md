# Story 5.7: Subscription State & Banners

Status: done

## Story

As a **user whose subscription state affects my experience**,
I want **to see my current plan status in the header, get a persistent banner if payment fails, and access a single upgrade dialog from any upgrade CTA**,
So that **I always know where I stand and can take action when needed**.

## Acceptance Criteria

**Given** the Subscription Chip in the header
**When** a free user views any page
**Then** the chip shows "Free — Upgrade" with:
- Transparent fill, {colors.primary} text, 1px {colors.primary} border
- {rounded.full}, 28px height
- The whole chip is a button that opens the Upgrade Dialog

**When** a Starter user views any page
**Then** the chip shows "Starter — renews on {date}" with:
- Solid {colors.primary} / {colors.primary-foreground}
- {rounded.full}, 28px height
- Date uses localized month name and Western numerals

**When** a cancelled user (access until date) views any page
**Then** the chip shows "Cancelled — access until {date}" with:
- {colors.warning-container} / {colors.warning-on-container}
- Clicking offers reactivation

**Given** the persistent failed-renewal banner (FR-28)
**When** a subscription has status 'failed_renewal'
**Then** a non-dismissible banner appears on ALL authenticated surfaces:
- {colors.danger-container} / {colors.danger-on-container}
- Compact 40px height
- "Payment failed — update your payment method to keep Starter" (localized)
- Link → Chargily update-payment page [AMENDED 2026-08-11, John PM verdict — the banner's "update your payment method" link performs the retry-payment redirect via POST /api/billing/create-checkout/ (type=subscription, 1,500 DZD — the 5.5 failed_renewal retry CTA precedent; the re-activated row is now-anchored per 5.5 D19). No Chargily update-payment URL exists in settings at V1 (only CHARGILY_SUCCESS/FAILURE_URL) and Chargily V1 has no customer portal; a settings-pinned CHARGILY_PAYMENT_URL constant is the pre-prod gate — verify Chargily's live payment-method surface at the docs gate (the 5.2 precedent) and re-point the link if one exists (one-line change)]
- No dismiss `X` — the banner persists until payment succeeds
- Prior-cycle credits remain usable until the next cycle would have begun

**Given** the Upgrade Dialog [AMENDED 2026-08-11, John PM verdict — the "0-credit recovery" entry point dispatches by user.tier: free users → the Upgrade Dialog; Starter users → a Recovery Dialog (top-up surface embedding the two add-on pack purchase paths via the shared create-checkout pack flow — never the Upgrade Dialog, whose Subscribe CTA the 409 would reject for an active subscriber). Both zero-credit recovery-stub toasts are replaced. Focus is trapped, Esc closes, focus returns to the invoking aria-disabled control]
**When** any upgrade CTA is clicked (header chip, 0-credit recovery, watermark modal, xlsx tooltip, daily-limit state) [AMENDED 2026-08-11, John PM verdict — the "daily-limit state" entry point is the SEARCH daily-limit state (FR-7: 30/day free, 100/day Starter): when a free user's Apply control is aria-disabled by the rate-limited phase, clicking it opens the Upgrade Dialog (disabled-but-actionable). The export 5,000-rows/24h limit (FR-20) is tier-independent and stays the come-back-tomorrow message — no dialog; upgrading cannot lift a defensive anti-scraping cap]
**Then** the same single Upgrade Dialog opens
**And** it contains:
- Starter plan details: 1,500 DZD/mo, 200 credits/mo, inclusions list
- "Subscribe via Chargily" button → Chargily checkout
- No public pricing page dependency — the dialog is the sole conversion surface

**Given** the Upgrade Dialog accessibility
**When** it opens
**Then** focus is trapped, Esc closes it, and focus returns to the invoking control
**And** on close, the user is not redirected (they stay on the current page)

**Given** the Subscription Chip [AMENDED 2026-08-11, John PM verdict — the chip renders FIVE states driven by the subscription row's status, never user.tier (the PlanCard precedent): free (no row) and expired both render the free variant — transparent fill, {colors.primary} text, 1px {colors.primary} border, {rounded.full}, 28px, whole chip opens the Upgrade Dialog; starter (active) — solid {colors.primary}/{colors.primary-foreground}, "Starter — renews on {date}" with a localized month name and Western numerals (AD-8); cancelled — {colors.warning-container}/{colors.warning-on-container}, "Cancelled — access until {date}", clicking opens the Upgrade Dialog (its Subscribe CTA is the reactivation path — the create-checkout 409 blocks only ACTIVE); failed_renewal — {colors.warning-container}/{colors.warning-on-container}, "Starter — payment failed", clicking performs the retry-payment redirect via POST /api/billing/create-checkout/ (type=subscription, the 5.5 retry precedent) — the persistent banner owns the danger-toned alarm and its copy]

**Given** the PlanCard CTAs [AMENDED 2026-08-11, John PM verdict — the PlanCard "Upgrade" (free) and "Resubscribe" (expired) CTAs open the Upgrade Dialog (the 5.5 D10 handoff — direct redirects replaced). The PlanCard "Reactivate" (cancelled) and "Retry payment" (failed_renewal) CTAs keep their shipped direct create-checkout redirects — recovery paths, not upgrade paths]

**Given** the upgrade copy [AMENDED 2026-08-11, John PM verdict — billing.upgrade_stub is deleted from all three locales; the i18n-shape test's truthy + verbatim pins and the export-modal xlsx-click toast assertion are updated to the dialog-open assertion in the same change (the 5.5 restore condition is met — the 4.5 consumer is replaced); billing.renewal_date is absorbed into billing.chip.starter (zero live consumers today)]
